# Stage 1 — Problem framing

## 1.1 The problem / opportunity

What is happening, for whom, how often, and what it costs them. Write it so a stranger could propose a solution you haven't thought of. No UI, flows, or architecture here.

## 1.2 Why it matters

Which strategy pillar, OKR, segment, or revenue line this serves. What happens if we do nothing for a year.

## 1.3 Target audience

Named persona or segment. Size if known. Who is explicitly *not* the audience.

## 1.4 Evidence

Every claim with its source. Mark assumptions.

| Claim | Evidence / source | Confidence |
|---|---|---|
| | e.g. 14 of 22 interviews, Oct 2026; ticket tag `filters` 310/mo; query `…` | High / Med / Low / Assumption |

## 1.5 Success metrics

What would prove this was worth doing. Baseline or a plan to measure one.

| Metric | Baseline | Target | How measured |
|---|---|---|---|
| | | | |

## 1.6 Competitive & alternative landscape

How users solve this today — competitors, workarounds, adjacent products. What they get right and wrong.

## 1.7 Potential directions

Two or more genuinely different approaches. Include "do nothing" or "buy/partner" when honest. Do not pick one here.

| Direction | What it bets on | Rough cost / effort | Main risk |
|---|---|---|---|
| A. | | | |
| B. | | | |
| C. Do nothing | | | |

## 1.8 Open questions for discovery

What we need to learn before solution framing, and how.

# Stage 2 — Solution framing

*Fill only after a recorded Stage 1 outcome of Proceed or Approved with corrections.*

## 2.1 Chosen direction and why

Which direction from 1.7, and in two or three sentences why it beat the others. Note course corrections from the Stage 1 review and how they were absorbed.

## 2.2 Key flows

Link to design artifacts. One paragraph on the experience from the persona's point of view. Behavioral detail belongs in the feature spec, not here.

## 2.3 Engineering approach

What it depends on, what it changes, what it must not touch — at the level a reviewer needs to judge risk. Not a design doc; the plan phase produces that from the spec.

## 2.4 Go-to-market

Positioning in one line, launch tier, enablement needed, pricing/packaging impact or "none", docs/support readiness.

## 2.5 Scope for this release

In / out, in a few bullets each. Out-of-scope items that are "later" get a note on when.

## 2.6 Risks & dependencies

| Item | Type | Likelihood / impact | Owner | Mitigation |
|---|---|---|---|---|
| | dependency / risk | | | |

## 2.7 Milestones

Target dates for spec approved, build, beta, GA, recap.

## 2.8 Success metrics check

Confirm or revise 1.5 given what discovery taught. Name the telemetry that must exist to measure them.
